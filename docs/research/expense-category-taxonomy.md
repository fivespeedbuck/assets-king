# 资产大王：个人消费分类体系调研与初始分类库建议

> 调研日期：2026-08-17
>
> 范围：个人日常记账的消费用途分类；不采用企业会计科目或税务科目。
>
> 结论性质：产品与数据模型建议，不代表已经修改源码。

## 结论先行

资产大王适合采用“交易类型 → 一级用途 → 二级用途”的结构，但消费统计只使用后两层：

- **交易类型**：消费、收入、退款、账户转账、信用卡还款、贷款还款、报销到账。
- **一级用途**：餐饮、出行、自驾、宠物、购物、生活缴费等。
- **二级用途**：堂食、外卖、地铁、停车、主粮、药品等。

“必要/非必要”“是否周期性”“是否待报销”“支付渠道”“资金账户”和“商户”都应是交易的独立属性，不能伪装成消费分类。尤其是必要性必须由二级分类给出默认值、每笔交易允许覆盖；自由开销只扣最终被标记为“非必要”的交易，不能再用“购物类全部算非必要”这种一级分类硬编码。

建议默认启用 13 个一级分类，覆盖用户已经确认的生活场景；旅行度假、育儿、住房维护、工作经营等低频或未确认场景放入“可选分类包”，需要时一键启用。这样既不逐项追问，也不会像某些软件一样首次使用就出现三十多个一级分类。

## 一手来源比较

### 1. Cashiro（开源 Android 自动记账）

Cashiro 的官方源码预置了较宽的两级分类库。一级包括 Food & Drinks、Transport、Shopping、Groceries、Home、Entertainment、Travel、Medical、Bill、Pet Care 等；二级进一步列出 Eating out、Take Away、Metro、Bus、Fuel、Parking、Medicines、Dentist、Rent、Water、Electricity、Vet 等。它还把 Self Transfer、Credit Bill、EMI 等放在同一个分类表里。[Cashiro 默认一级与二级分类源码](https://github.com/ritesh-kanwar/Cashiro/blob/main/app/src/main/java/com/ritesh/cashiro/di/DatabaseModule.kt#L292)

可复用之处：两级粒度、宠物/医疗/账单等日常覆盖，以及商户自动分类需要的稳定叶子分类。

不应照搬之处：一级分类过多，并把消费用途、还款和转账混在一起；Swiggy、Zomato、Uber 等具体品牌也不应成为二级分类，品牌应该进入商户库和映射规则。

许可证边界：Cashiro 为 AGPL-3.0。本文只借鉴公开的产品结构和通用词汇，不复制其种子代码、图标或实现。

### 2. Money Manager Ex（成熟开源个人财务软件）

Money Manager Ex 的官方数据库仓库直接公布了初始化层级：Bills 下有 Telephone、Electricity、Gas、Internet、Rent、Water；Food 下有 Groceries、Dining out；Automobile 下有 Maintenance、Gas、Parking、Registration；Healthcare 下有 Dental、Eyecare、Physician、Prescriptions；另有 Education、Insurance、Vacation、Gifts、Income 和 Transfer。[Money Manager Ex 初始化分类层级](https://github.com/moneymanagerex/database#initialization)

可复用之处：一级少、二级清楚，生活缴费、自驾、医疗健康天然适合独立一级分类。

不应照搬之处：Video Rental、Cable TV 等条目已经过时；Transfer 是交易类型而非消费用途；面向中国用户还需要微信/支付宝支付渠道、共享电瓶车、高铁等本地场景。

许可证边界：该数据库仓库为 GPL-2.0；同样只借鉴产品信息，不复制实现。

### 3. Monarch Money（成熟商业个人财务产品）

Monarch 官方帮助文档明确采用三层结构：Type（Income、Expenses、Transfers）→ Group（Housing、Food）→ Category（Rent、Groceries），并提供约 60 个系统类别，让用户停用 Education、Children、Auto、Business 等不适用类别。官方还明确把 Transfer 和 Credit Card Payment 排除在预算与现金流之外。[Monarch 分类与预算说明](https://help.monarchmoney.com/hc/en-us/articles/360048883631-Budgets)

可复用之处：交易类型与用途分类分离；不适用的系统类别是“停用/归档”，不是删除；转账和信用卡还款不计消费。

不应照搬之处：约 60 个默认类别对单人本地 App 偏重，且美国住房、教育与商业场景不必默认展示。

### 4. YNAB（成熟预算产品，作为分类设计原则补充）

YNAB 的官方资料说明其默认组会覆盖 Bills、Frequent、Non-Monthly、Goals、Quality of Life Goals，并举出 groceries、transportation、eating out、travel、education、health、hobbies 等类别；同时强调分类会随着用户生活变化而调整，而不是追求固定数量。[YNAB 默认分类组与可定制原则](https://www.ynab.com/blog/how-many-ynab-categories)

YNAB 的餐饮模板把 Grocery Store、Warehouse Club、Not Cooking、Coffee、Treats 分开，另一篇官方文章还按 Time with friends、Work lunches、Fast food、Date night、Convenience、Coffee Break 拆解外食动机。这支持资产大王把“堂食/外卖/买菜”和“嘴馋加餐/请朋友吃饭”分开，因为用户关心的不只是在哪吃，也关心是否值得。[YNAB 餐饮模板](https://www.ynab.com/blog/4-myths-of-meal-planning-busted)、[YNAB 外食动机分类](https://www.ynab.com/blog/do-you-spend-too-much-eating-out-try-this)

可复用之处：分类应服务于消费决策；对用户真正想控制的大类可以更细，其余保持简洁。

不应照搬之处：Bills、Non-Monthly 是预算频率/计划维度，不应直接成为资产大王的消费用途。

### 5. HomeBank（成熟开源个人财务软件）

HomeBank 的上游预置分类数据覆盖 Automobile、Bills、Education、Health-care、Hobbies/Leisure、Household、Pet Care、Travel/Vacation 等一级，并细分燃油、维修、手机、电水燃气、处方药、宠物食品/用品/兽医、住宿等。它能补足 Money Manager Ex 较旧分类中缺少的宠物和现代生活场景。[HomeBank 预置分类数据](https://sources.debian.org/src/homebank/5.9.7-1/data/datas/hb-categories-en.csv/)

可复用之处：医疗、宠物、家居、个人护理的覆盖完整，适合作为漏项检查表。

不应照搬之处：其中包含房贷、Medicare、州税等美国口径，Food、Groceries、Dining Out 也存在重叠；资产大王应重新整理为原创中文层级。

许可证边界：HomeBank 为 GPL-2.0-or-later。不要复制整张 CSV、排序和描述，只参考多个来源的共同生活概念。

### 6. Plaid Personal Finance Category v2（现代交易语义补充）

Plaid 官方交易接口使用 `primary` 与 `detailed` 两级个人财务分类，官方完整表覆盖 FOOD_AND_DRINK、GENERAL_MERCHANDISE、MEDICAL、PERSONAL_CARE、TRANSPORTATION、TRAVEL、RENT_AND_UTILITIES，也单独建模 INCOME、LOAN_PAYMENTS、TRANSFER_IN/OUT 等交易语义。[Plaid Transactions API](https://plaid.com/docs/api/products/transactions/)、[Plaid PFC v2 完整分类表](https://plaid.com/documents/pfc-taxonomy-all.csv)

可复用之处：能校验咖啡/餐厅/买菜、宠物用品/兽医、共享出行/公共交通、停车/高速、房租/水电气等现代场景是否遗漏，也进一步佐证“转账与还款不是消费用途”。

不应照搬之处：Plaid 分类表不是开源数据，且面向金融数据聚合服务；这里只用于验证抽象和覆盖面，不复制其代码值、英文描述或完整编排。

## 跨来源得到的设计规则

1. **只保留两级用途分类。** 更多层级会让待确认变慢；项目、旅行或特定人物可在未来用标签表达。
2. **交易类型先于分类。** 转账、信用卡还款、贷款还款、退款、报销到账不进入消费饼图，也不占分类预算。
3. **周期性是计划属性。** 手机话费可以同时是“生活缴费 / 手机话费”和“每月周期账单”，不需要再建“订阅”一级分类。
4. **商户不是分类。** 美团、淘宝、微信、支付宝不能成为用途；它们分别是商户线索或支付渠道。标准商户映射到二级用途。
5. **必要性不是一级分类。** 同属餐饮的“买菜”与“嘴馋加餐”必要性不同，同属购物的“日用品”与“兴趣爱好”也不同。
6. **默认库可停用、不可物理删除。** 已产生历史流水的类别改为归档；名称可改，但稳定 ID 不变。
7. **无法可靠归类时宁可待分类。** 不要为了填满字段而把交易塞进“其他”；确认时允许就地新增二级分类。

## 建议的初始消费分类库

必要性标记含义：

- `必要`：默认计入必要生活预算。
- `非必要`：默认从自由开销额度扣除。
- `按场景`：确认卡仍预填一个建议，但必须允许一键切换；后续可学习用户选择。

| 一级分类 | 默认二级分类（默认必要性） | 说明 |
| --- | --- | --- |
| 餐饮 | 买菜（必要）、堂食（必要）、外卖（按场景）、零食饮料（非必要）、嘴馋加餐（非必要）、请朋友吃饭（非必要）、其他（按场景） | 保留用户希望观察的餐饮动机；“朋友请客”如果本人没有付款，不应生成消费流水。 |
| 出行 | 公交（必要）、共享电瓶车（必要）、地铁（必要）、打车（按场景）、高铁（按场景）、飞机（按场景）、其他（按场景） | 支付方式或出行工具是用途；公务差旅可再标记待报销。 |
| 自驾 | 加油（必要）、充电（必要）、停车（必要）、高速费（必要）、洗车（非必要）、保养（必要）、维修（必要）、保险（必要）、违章（非必要）、其他（按场景） | 与公共出行分开，便于看清养车成本；违章仍是真实支出，但不应算必要生活预算。 |
| 宠物 | 主粮（必要）、零食（非必要）、用品（按场景）、医疗（必要）、驱虫疫苗（必要）、洗护美容（非必要）、寄养（按场景）、其他（按场景） | 采用用户已确认的分类。 |
| 购物 | 日用品（必要）、服饰鞋包（按场景）、数码电器（按场景）、家居用品（按场景）、美妆护理用品（按场景）、兴趣爱好（非必要）、礼物（非必要）、其他（按场景） | “美妆护理用品”指商品；理发、美容服务放个人护理，避免重叠。 |
| 生活缴费 | 房租（必要）、水费（必要）、电费（必要）、燃气费（必要）、手机话费（必要）、其他（按场景） | 按用户现状不默认显示物业费和宽带，需要时从可选项添加。 |
| 医疗健康 | 挂号就诊（必要）、药品（必要）、体检（必要）、牙科（必要）、康复理疗（必要）、其他（按场景） | 美容、健身不混入医疗，避免把可选消费误算必要支出。 |
| 个人护理 | 理发（按场景）、洗护服务（按场景）、美容美甲（非必要）、按摩放松（非必要）、其他（按场景） | 仅放服务，商品仍归购物。 |
| 娱乐休闲 | 电影演出（非必要）、游戏（非必要）、KTV（非必要）、桌游剧本杀（非必要）、线上娱乐（非必要）、其他（非必要） | 全部默认进入自由开销；影音/游戏会员仍归这里，周期性另外标记。 |
| 运动健身 | 健身会员（非必要）、运动课程（非必要）、场地费用（非必要）、器材装备（按场景）、营养补剂（按场景）、其他（按场景） | 医嘱康复改归医疗健康。 |
| 学习成长 | 书籍资料（按场景）、课程培训（按场景）、考试认证（按场景）、文具办公（按场景）、其他（按场景） | 对职业必需与兴趣学习允许逐笔改变必要性。 |
| 人情往来 | 红包礼金（非必要）、孝敬家人（按场景）、公益捐赠（非必要）、其他（按场景） | 餐饮请客仍归餐饮，以保留用户最关心的餐饮消费构成；不要重复记两类。 |
| 其他 | 待分类（按场景） | 兜底只用于尚未确认的流水；确认完成原则上不应长期停留在这里。 |

## 可选分类包（默认不展示）

这些类别应保留为模板，需要时一键启用或由用户在确认页新增：

| 可选一级分类 | 建议二级分类 | 启用条件 |
| --- | --- | --- |
| 旅行度假 | 住宿、景点门票、旅行服务、当地交通、纪念品、其他 | 用户希望把整次旅行作为独立开销大类，而不是分别统计餐饮/出行时。 |
| 住房维护 | 家具家装、维修、保洁、搬家、其他 | 发生自有住房、装修或独立家政成本时。 |
| 保险税费 | 商业保险、个人税费、银行费用、证件工本费、其他 | 非自驾保险或真实金融服务费开始频繁出现时。 |
| 数字工具 | 软件工具、云存储、域名服务器、其他 | 生产力软件和个人云服务无法合理归入学习/娱乐时。 |
| 家庭育儿 | 托育、教育、用品、医疗、活动、其他 | 有稳定育儿支出时。 |
| 工作经营 | 办公、差旅、软件、营销、物流、税费、其他 | 出现个人经营或副业账务时；否则不要让企业科目污染个人记账。 |

## 不应出现在消费分类库里的项目

| 项目 | 正确归属 | 原因 |
| --- | --- | --- |
| 账户转账、微信零钱充值、ATM 取现 | 交易类型：账户转账 | 只是资产位置变化，不是消费。 |
| 信用卡还款 | 交易类型：信用卡还款 | 消费已经在刷卡时记录，二次计支出会重复。 |
| 贷款还款 | 交易类型：贷款还款 | 本金减少负债；利息和费用才是真实支出明细。 |
| 退款 | 交易类型：退款并关联原消费 | 应冲减原分类与原必要性，不应算普通收入。 |
| 报销到账 | 交易类型：报销到账并关联垫付款 | 增加账户余额，但应冲减个人支出而非工资收入。 |
| 周期账单、订阅、代扣 | 交易/计划属性 | “多久扣一次”与“钱花在哪”是两个维度。 |
| 微信、支付宝、银行卡 | 支付渠道/资金账户 | 不能替代商户或用途分类。 |
| 美团、淘宝、京东等 | 标准商户或平台线索 | 同一平台可能买菜、外卖、日用品或数码商品，不能固定等于一个分类。 |

## 对资产大王现有模型的影响（后续开发参考）

当前 `TransactionCategory` 是固定枚举，只有十余个一级分类；`defaultOptionalCategories` 又按整个一级分类判断自由开销。这无法表达“餐饮里的必要与非必要”“购物里的日用品与兴趣爱好”，也无法安全地重命名、归档和新增二级分类。

后续实现应至少满足：

1. 一级、二级分类改为数据库实体，使用稳定 ID；显示名称可修改。
2. 二级分类保存 `defaultNecessity`，交易自身保存最终 `necessity`，历史统计以交易值为准。
3. 分类支持启用、归档、排序和父级调整；有历史流水的类别不物理删除。
4. 标准商户、通知原始商户别名与二级分类映射独立保存。
5. 周期、报销、退款关联、账户、渠道和交易类型均为独立字段，不再占用分类字符串。
6. 迁移旧枚举时先做显式映射；旧 `DINING` 等数据保留到对应一级分类，无法确定二级时进入该一级的待补分类队列，不能静默猜测。

## 推荐采用的产品默认值

- 首次升级自动创建上述初始库，保留现有历史分类映射。
- 分类选择器先显示最近使用和商户建议，再显示完整两级库。
- 新商户确认成功后学习“标准商户 → 二级分类 → 默认必要性”，但本次交易的逐笔修改优先于商户规则。
- 设置中提供“恢复系统分类模板”，只补回缺失模板，不覆盖用户改名、归档和必要性调整。
- 初始库不是最终真理：统计积累后提示合并长期不用的类别或拆分过大的类别，但绝不自动改历史分类。

## 最终建议

可以停止逐个询问医疗、娱乐、学习等分类。直接采用本文件的初始库作为产品默认值，再让用户在“分类库”和待确认页中随时增删、改名、归档和调整必要性。尚未明确的生活场景放在可选分类包，不阻塞当前需求访谈和后续开发。
